<p>访问出问题的时候，人容易直接跳到结论："肯定是 IP 被墙了"或"机房 IP 一定被识别"。这两种判断都对过，也都错过。更靠谱的做法是画一棵故障树，从现象往下逐层分叉，每一支给出可验证的判据。这篇按故障树的结构写：连接有没有建立、建立了有没有被拦、没被拦为什么还是用不了，最后给一条从根到叶的排查顺序。住宅和机房的差异，在树的第二支才真正体现出来。</p>

<h2>一、先画树：一次访问失败往下分三支</h2>
<p>树根是"访问失败"这个笼统现象。往下第一层只问一件事：TCP 连接建立了吗。这一问能把问题分成两半，一半在网络，一半在应用。</p>
<h3>三个判断节点</h3>
<p>节点一，连接是否建立：用 <code>nc -vz 目标域名 443</code> 或 <code>telnet 目标域名 443</code>，几秒内有响应就是通了，超时就是没通。节点二，通了之后服务端返回什么：用 <code>curl -I https://目标域名</code> 看状态码，200 和 3xx 是正常路径，403、429、503 是拦截或限流，5xx 是服务端故障。节点三，前两步都正常但业务还是失败，问题在账号、客户端或数据本身。</p>
<h3>为什么先分层再归因</h3>
<p>因为三层的修复成本差很多。网络层换个出口就能试，应用层要改请求特征，账号层可能要申诉。跳过前两层直接怀疑平台识别，往往花了钱换 IP，问题还在。</p>

<h2>二、第一支：连接根本没建立</h2>
<p>这一支与住宅还是机房基本无关，属于纯网络问题。查三件事：本地出站、代理端口、目标端口。</p>
<h3>本地出站先排除</h3>
<p>企业网络只放行 80 和 443 的情况很常见。代理端口是 8080 或 1080 时，连接会被本地防火墙静默丢弃，现象是超时而不是拒绝。用 <code>curl -x http://地址:端口 -v https://ipinfo.io</code>，如果卡在 <code>Connected to</code> 之前，就是出站被拦。</p>
<h3>代理侧与目标侧</h3>
<p>代理侧要看控制台里线路状态是否为"运行中"，有些线路在到期或超额后会进入"已暂停"，此时端口仍监听但不转发。目标侧要看目标站是否对来源地区做了整体限制，用同一线路访问其他站点做对照，能快速区分是"这条线坏了"还是"这个站不让进"。</p>

<h2>三、第二支：连上了但被拦</h2>
<p>住宅与机房的差异，主要在这一支。拦截通常来自三类判据：地址属性、行为特征、账号历史。</p>
<h3>地址属性看什么</h3>
<p>三个公开可查的字段：ASN 类型、rDNS、地址段用途。用 ipinfo.io 或 bgp.he.net 查一个地址，ASN 的 type 字段会写 isp、hosting 或 business；rDNS 反解出来像 <code>static-1-2-3-4.isp.example.net</code> 的和像 <code>vm-1234.cloud.example.com</code> 的，含义不同。机房地址多为 hosting 类型，rDNS 带 cloud、server、vps 字样；住宅地址多为 isp 类型，rDNS 常带 city 或业务线缩写。这不是判定"能不能过"的标准，只是一个可观测的差异。</p>
<h3>行为特征往往比地址更关键</h3>
<p>同一出口在短时间内发起大量请求、请求间隔高度规律、User-Agent 与浏览器指纹不匹配、缺少正常的静态资源请求，这些特征组合起来，比"这个 IP 属于机房"更能触发拦截。反过来说，机房 IP 做低频、正常的交互，被拦的概率并不高；住宅 IP 高频刷接口，一样会撞上 429。</p>

<h2>四、第三支：通了没被拦，还是用不了</h2>
<p>这一支最容易被误判成 IP 问题，实际上和出口关系不大。</p>
<h3>账号侧的信号</h3>
<p>登录后立刻要求验证、功能入口缺失、订阅状态显示异常、对话中途被中断并提示稍后再试，这些更像账号或会话层面的状态。判断方法很简单：换一条完全不同的线路，用同一账号登录，如果现象一致，就与出口无关。</p>
<h3>客户端与环境</h3>
<p>时区、语言、DNS 解析结果、浏览器指纹不一致，都会造成"能打开但用不了"。特别提一句 DNS：用 <code>socks5</code> 而不是 <code>socks5h</code> 时，域名在本地解析，可能出现解析到就近节点、与实际出口地区不匹配的情况。换成 <code>socks5h</code> 或显式指定 DNS，往往就能解决。</p>
<h2>五、按树走一遍的排查顺序</h2>
<h3>五步定位法</h3>
<p>第一步，换一个目标站访问，确认是否单站问题。第二步，用 nc 测端口，确认连接层。第三步，curl 看状态码，确认是拦截还是服务端故障。第四步，查 ASN 与黑名单，确认地址属性。第五步，换账号或换设备复现，确认是否账号侧。每一步都留下记录，别凭记忆跳步。</p>
<h3>什么时候该换线路</h3>
<p>只有在前四步都指向地址属性、且换一条同类型线路后现象消失时，才值得换。如果换了三条线路现象依旧，问题八成在自己的请求特征或账号状态上，继续换 IP 只是花钱买心理安慰。</p>

<h2>常见问答</h2>
<h3>机房 IP 一定会被识别出来吗？</h3>
<p>答：地址属性是公开可查的，ASN 类型写着 hosting，任何人查一下就知道。但"知道"和"拦截"是两件事，很多平台只在异常行为出现时才启用这类判据。</p>
<h3>住宅 IP 就不会被拦吗？</h3>
<p>答：不会。住宅地址同样可能进黑名单，也可能因为行为异常被限流。地址只是众多信号之一，不是通行证。</p>
<h3>怎么快速判断是 IP 问题还是账号问题？</h3>
<p>答：交叉验证。同账号换线路、同线路换账号，两组各做一次。现象跟着账号走就是账号问题，跟着线路走就是线路问题，都不跟就是客户端或目标站问题。</p>
<h3>被拦之后等多久再试比较合适？</h3>
<p>答：看返回类型。429 通常等几分钟到一小时，403 可能需要更久，且要改变请求特征才有意义。盲目高频重试只会延长限制时间。</p>

<h2>合规提示</h2>
<p>本文的排查方法用于定位自有系统的网络与配置故障，不构成规避平台风控的建议。使用任何线路都应遵守目标平台的服务条款，按正常频率与方式访问。</p>
<p>地址属性查询请使用公开合规的查询服务，不要对第三方地址段做扫描探测。涉及他人网络的行为可能触犯法律。</p>
<p>故障树中的判据为经验总结，不同平台的风控策略并不公开，实际表现可能存在差异。</p>
